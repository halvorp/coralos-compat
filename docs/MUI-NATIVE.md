# muimaster.library (MUI / Zune) translated natively onto guestui

Ruling 17 for the second Amiga toolkit: MUI becomes ONE table (`src/translate/mui.rs`) plus small adapters, projected through
the shared `retro-translate` registry. Nothing is drawn by MUI code: the object tree is a HOST-side model, the pixels are the
native UI's, and no code path names an application (`tools/check-translation-seam.sh`).

## How the compiled program calls MUI
- `ApplicationObject, ... End` etc. are `muimaster.library/MUI_NewObjectA(a0 = "Application.mui", a1 = taglist)`;
  `MUI_MakeObjectA(d0 = type, a0 = params)`; `MUI_DisposeObject(a0)`; `MUI_CreateCustomClass`/`MUI_DeleteCustomClass`.
- `set(obj, tag, v)` is `SetAttrs` -> `intuition.library/SetAttrsA`; `get` is `GetAttr`.
- `DoMethod(obj, id, ...)` is amiga.lib code INSIDE the guest: `a2 = obj; a0 = *(obj - 4)` (`o_Class`); `a1 = &msg`; jump to the
  class's `h_Entry`. A native MUI class's `h_Entry` is ONE shared trap slot (`boopsi.rs`); a program's own subclass has the
  program's dispatcher there, which reaches the native half with its own `DoSuperMethod`.

## The pieces (`src/mui/`)
| file | concern |
|---|---|
| `classes.rs`, `attrs.rs` | the 29 classes (Zune's `_MUI_*_desc`: name + super) and what each accepts; an unknown class or attribute is a NAMED refusal |
| `ids_gen.rs`, `names.rs` | GENERATED by `tools/gen-mui-ids.py` from MUI's `libraries/mui.h` and Zune's class headers: every number is a fact, none hand-typed |
| `object.rs`, `methods.rs`, `notify.rs` | lifecycle, SetAttrs/GetAttr (symbolic values resolved: `ActivePage_Next`, `Cycle_Active_Next`, Numeric/Gauge clamps), methods, `MUIM_Notify` |
| `app.rs`, `hooks.rs` | the Application: ReturnIDs, the inbox of native events (applied inside the program's own `NewInput`), `MUIM_Application_Execute` (a 64-byte guest loop), `MUIM_CallHook` and notifications aimed at a program's own class as GUEST CALLS |
| `roles.rs`, `layout.rs`, `win.rs` | what an object IS (the class contract), where it goes (MUI's grid layout over the real screen-font metrics), the window that holds the projection |
| `input.rs` + `translate/mui.rs` | the intents back: role x intent -> the `set` calls MUI's classes make |
| `make.rs`, `list.rs`, `menu.rs`, `custom.rs` | `MUI_MakeObjectA`, the List class (entries, hooks), menu strips, subclasses of MUI classes |

## Roles (the closed vocabulary, grown only with a producer)
Text / Rectangle / Image with `MUIA_InputMode` -> button / toggle / checkbox (`MUII_CheckMark`); static Text -> label (a `MUIO_Label`
is the label of the control after it); String -> field; Cycle / Radio / Register -> `Choice{Cycle|Radio|Tabs}`; Slider; Gauge;
Prop / Scrollbar -> scrollbar; List (under its Listview) -> `List`; a framed container -> group. Rectangle spacers and bars,
Balance, Area, Scrollgroup, Virtgroup, other Images and plain Groups have no role (layout only). A page-mode Group and a Register show
only the ACTIVE page's controls: a page turn retires one page's controls and adds the other's (a new generation each).

## The table (what a native intent does, exactly as `area.c` / `string.c` / ... do it)
Button: `Press` = `set(Selected, Pressed)` TRUE together then `Timer+1`; `Release inside` = `Pressed` FALSE then `Selected` FALSE
(only while Selected); `Release outside` = `nnset(Pressed)` then `Selected` FALSE (no Pressed notification); `Activate` = all of
it. Toggle/checkbox flip `Selected` and `Pressed`; Slider -> `MUIA_Numeric_Value`; Choice -> the class's `Active` (tabs: `ActivePage`);
Field -> `String_Contents` then `String_Acknowledge` (whose notification carries the contents pointer); Scrollbar ->
`MUIA_Prop_First`; List -> `MUIA_List_Active`. MUI posts nothing beyond the notifications `set` runs, so no row has a post. A menu pick
follows `window.c`: a checkable item toggles, `Menuitem_Trigger`, the application's and the window's `MenuAction` are set to the item's
`MUIA_UserData`, and the UserData is returned as a ReturnID.

## Events and the program's own loop
`Amiga::deliver` offers a native event to `mui::try_deliver` first. It is validated at once (a stale control generation, an intent the role
has no row for, or a value the control does not hold is a named refusal) and then QUEUED on the owning Application, which wakes its task.
MUI processes input inside `MUIM_Application_NewInput`, in the program's task, so that is where the table's `set` calls, the
notifications, the guest hooks they queue, and the ReturnIDs happen. Tests that have no running program call `mui::app::pump`.

## Subclasses (`MUI_CreateCustomClass`)
A real BOOPSI class over the native MUI class (`MakeClass` + the dispatcher in `h_Entry`/`h_SubEntry`, a real `struct MUI_CustomClass`).
`OM_NEW` reaches the native class through `DoSuperMethod`: rootclass allocates the instance (the program's instance data lives in it),
then the MUI half is made from the tags that are MUI's (`0x8042xxxx`, `0x9042xxxx`; the program's own attributes pass through unseen,
as in BOOPSI). The subclass's role is its nearest standard ancestor's, because it uses that ancestor's state. The drawing pipeline
(`MUIM_Setup/AskMinMax/Show/Draw`) is sent to a subclass that draws itself: see "Objects that draw themselves".

## Objects that draw themselves (`mui/drawn.rs`, `mui/surface.rs`)
An instance of a guest class over Area.mui that has no role of its own (nothing else claims it: ruling 17 piece 4) is a content PLANE.
MUI sends it, as guest calls to its own dispatcher and in Zune's order (window.c): `MUIM_Setup` for the tree, `MUIM_AskMinMax` (its answer
sizes it in the layout: default size, and it stretches where Max > Def), the native window opens, `MUIM_Show`, then `MUIM_Draw` with
`MADF_DRAWOBJECT`; a resize that moves or grows it, or `MUI_Redraw`, sends `MUIM_Draw` again; closing sends `MUIM_Hide`, `MUIM_Cleanup`.
The steps are queued like a notification's hook, so the window is open and drawn before `SetAttrs(win, MUIA_Window_Open, TRUE)` returns,
and a resize's draw runs in the program's loop (`NewInput`). The class reads its place straight out of its object (`_left(obj)`,
`_mwidth(obj)`, `_rp(obj)`: `mad_Box`, `mad_MinMax`, `mad_RenderInfo` written by `mirror.rs`) and draws into the window's real RastPort
(`window::make_surface_window`: a struct Window with a canvas and layer; `MUI_AddClipRegion` / `MUI_RemoveClipRegion` install real clip
regions). The graphics layer records those RastPort calls as a replayed plane in the object's rectangle. The native Area half answers what
Zune's `area.c` answers when the dispatcher passes a method up: no frame and no inner spacing (AskMinMax sums are 0), the host's own
background (Draw and DrawBackground draw nothing).
NOT done: frames and inner spacing of such objects, `MADF_DRAWUPDATE` partial redraws, off-screen buffers a class draws through with
`MUIM_DrawBackground` into its own bitmap (the native Area draws no background, so an off-screen buffer starts as the program cleared it).

## Handlers that fire (`mui/handlers.rs`)
`MUIM_Application_AddInputHandler` (`struct MUI_InputHandlerNode`: ihn_Object 8, ihn_Millis(UWORD) / ihn_Signals(ULONG) 12, ihn_Flags 16,
ihn_Method 20): with `MUIIHNF_TIMER` the node is a deadline on the engine's VIRTUAL clock (`next_timer_deadline` / `advance_clock_to`, the same
clock `timer.device` and `Delay` use). When it is due the application's task is woken; its next `NewInput` re-arms the node from the clock at
that moment (Zune's `SendIO` of the timerequest) and sends `DoMethod(ihn_Object, ihn_Method)`. Without the flag the node waits for `ihn_Signals`:
`NewInput` returns `1<<sigbit | every handler's signals` for the program's `Wait`, and the Execute loop keeps `Wait`'s result, so the node's method
runs when its signals woke the program (a program that passes 0 gets "all signals set", as application.c does: handlers run once at start).
A 0 ms timer is a named refusal (it would fire without end).
`MUIM_Window_AddEventHandler` (`struct MUI_EventHandlerNode`: ehn_Priority 9, ehn_Flags 10, ehn_Object 12, ehn_Class 16, ehn_Events 20): a native
pointer or key event for the window becomes the `struct IntuiMessage` Intuition would send (`content_input::pointer_message`, shared with plain
windows) and window.c's `HandleInputEvent` / `HandleRawkey` offer it to the nodes in list order (priority, then address, both descending): a node
whose `ehn_Events` has the class and whose object is enabled (with `MUI_EHF_GUIMODE`: can draw and is shown) gets `MUIM_HandleEvent(imsg, muikey)`
through `CoerceMethod(ehn_Class)` or `DoMethod`, and `MUI_EventHandlerRC_Eat` ends the walk. RAWKEY visits the active object's nodes, the default
object's, then the rest. NOT modelled: the user's MUI key preferences (`muikey` is always `MUIKEY_NONE`), virtual-group clipping of a press, drag
and drop. `OM_SET` / `MUIM_Set` on an object of a program's own class go through ITS dispatcher first (`SetAttrs` is `DoMethod(OM_SET)`); the
subclass's `DoSuperMethod` reaches the native half, which acts on the attributes of its own chain and ignores (with a log line) a MUI-range tag no
class of the chain defines, as BOOPSI does.

## Image classes (`mui/images.rs`)
`Bitmap.mui`, `ChunkyImage.mui`, `Bodychunk.mui` and `Imagedisplay.mui` DRAW: each image object in a window's layout gets a content plane
(`present_plane`, id = the object) in its rectangle. Sizes are Zune's `MUIM_AskMinMax` (Bitmap family min = default 1x1, Imagedisplay min 3, default 16;
all stretch; `MUIA_FixWidth/Height` apply). A Bitmap draws the program's `struct BitMap` (`MUIA_Bitmap_Bitmap`, `Width`, `Height`) from the object's
top-left, clipped to its box (bitmap.c), with `MUIA_Bitmap_SourceColors` (ULONG R,G,B per pen) or the screen palette (through `MappingTable`), and
`MUIA_Bitmap_Transparent` leaves that pen's pixels out. A ChunkyImage holds `width * height` pen bytes (row stride `MUIA_ChunkyImage_Modulo`) and a
3-byte RGB palette of `NumColors` <= 256. A Bodychunk decodes an ILBM BODY (planar rows padded to 16 bits, `depth` planes, an optional mask plane
skipped, optional ByteRun1). All are `Pixels` ops (one op, or one per opaque run when a pen is transparent). An Imagedisplay's `MUIA_Imagedisplay_Spec`
(`<type>:<data>`, imspec.c) becomes theme data where the spec is a NAMED thing: type 0 standard backgrounds -> `Fill` roles (the two-tone patterns
in their first pen), type 1 standard images -> arrows and the check mark as `Line` ops in the text pen, disk / hard disk / volume / drawer / chip /
network as host `Icon` roles, type 2 pens -> MUI pens as `Fill` roles and colormap pens as pixels. NOT drawn, each a named refusal: types 3..7 (an image
file through a picture datatype, gradients, vectors), system and RGB pen specs, the standard images with no glyph (cycle, popup, tape, knob, radio
button). A ChunkyImage / Bodychunk whose parameters make Zune's `make_bitmap` fail (no pixels, no size, 0 or > 256 colours, depth > 8) refuses by name:
Zune's `MUIM_Setup` would return FALSE and the window would not open.

## Classes on disk (`.mcc` / `.mcp`, `mui/disk.rs`)
A class that is not built in is a real disk library: `MUI_NewObjectA("Foo.mcc")` and `MUI_CreateCustomClass(.., "Foo.mcc", ..)` open it
through the disklib (its init and Open run in the guest), call `MCC_Query(0)` (then `(1)`, the preferences class) as a guest call and take
`mcc_Class` of the `MUI_CustomClass` it returns, exactly as Zune's `ZUNE_GetExternalClass`. Search order: `Zune/X`, `Classes/Zune/X`,
`MUI/X`, `mui/X` as OpenLibrary names (LIBS:, PROGDIR:), then `MUI:Libs/mui/X` and `SYS:Classes/Zune/X`. A class stays loaded (no Expunge);
`DiskClass.users` counts the objects and subclasses holding it. The class is then an ordinary guest `IClass`: its dispatcher is guest code,
its superclass chain reaches the native classes through the one dispatch path, its role is its nearest standard ancestor's.
What a guest subclass reads straight out of its object (`mui/mirror.rs`): Notify.mui's instance data is a `MUI_NotifyData` (28 bytes) and
Area.mui reserves room for `MUI_AreaData`, so a class's `_app(obj)` / `muiUserData(obj)` macros (plain offsets) read the application
and user data the host writes there (state stays host-side; a guest write is never read back). Without that, a class that calls
`DoMethod(_app(obj), ...)` jumps through a NULL object.
`OM_DISPOSE` follows Zune's family order (`mui/dispose.rs`): an object's own dispatcher first, then each child through ITS dispatcher
(`MUI_DisposeObject(child)`), then the free; a disk class's use count goes down with each object.

## Pens, display modes, settings (mui4 lane)
* `MUI_ObtainPen` / `MUI_ReleasePen` (`mui/pens.rs`): a `struct MUI_PenSpec` string (`m<n>` MUI pen, `p<n>` colormap entry, `s<n>` DrawInfo pen, `r<R>,<G>,<B>` 32-bit
  hex) becomes a pen of the screen's Gute Form palette through the existing `ObtainBestPenA` allocator; an allocated pen carries bit 16 so
  `MUI_ReleasePen` gives it back; out-of-range or unparsable specs are -1. The window's `MUI_RenderInfo` now holds `mri_DrawInfo`, `mri_Colormap`
  (offsets from m68k gcc) and `mad_RenderInfo` is set BEFORE the object's own `MUIM_Setup` (window.c `DoSetupMethod`). `MUIM_GetConfigItem` finds nothing:
  Zune's configuration dataspace holds only what the user saved, the defaults live in the asking class.
* `BestModeIDA`, `GetDisplayInfoData` `DTAG_DIMS` / `DTAG_NAME` over the one CoralOS mode (0x29000): 640x256x8, no overscan, 8-bit guns, a 256-pen
  palette; `BestModeIDA` applies bestmodeida.c's filters (monitor ID passes, DIPF must/must-not, depth, size) to it. `DTAG_MNTR` stays a named refusal.
* `MUIA_NoNotify` TRUE anywhere in one `SetAttrs` list silences the notifications of the whole call (Notify.mui `OM_SET`; `nnset`). Before this the
  engine notified anyway, and a Prefs editor's own widget updates recursed through their notifications until the stack ran into the program's data.
* `OM_ADDMEMBER` / `OM_REMMEMBER` on an Application add and remove windows after creation (a leaving window closes first).
* `Semaphore.mui` and `Dataspace.mui` (`mui/store.rs`; Dataspace over Semaphore): obtain/release with nesting, an Obtain that would block is a named
  refusal (cooperative scheduler, no wait queue), Attempt answers FALSE; Dataspace Add/Find/Remove/Clear/Merge with the node bytes in guest memory.
  `MUIM_Application_Load` / `Save` read and write `ENV:Zune/<MUIA_Application_Base>.cfg` (or `ENVARC:`, or a name), an IFF `FORM PREF` with a `MUIO`
  chunk, and export/import the NATIVE classes as Zune does (Group -> children, Window -> root, Cycle/Radio LONG, Numeric value, String contents, other
  Areas the selected byte, Text nothing; only objects with a `MUIA_ObjectID`). Objects of a program's own class are NOT sent `MUIM_Export` /
  `MUIM_Import` (the log line counts them); a program's own `IFFHandle` (`MUIM_Dataspace_ReadIFF/WriteIFF`) is a named refusal until iffparse exists.
* utility.library `AllocateTagItems`, `CloneTagItems`, `FreeTagItems`, `RefreshTagItemClones`, `TagInArray`, `FilterTagItems`, `MapTags`.
* The AROS volume's `LIBS:` also reaches `SYS:Classes` (S/Startup-Sequence: `Assign LIBS: SYS:Classes ADD`), where the BOOPSI gadgets
  (`colorwheel.gadget`, ...) live; the census tool and the AROS test helper assign it.

## Not done (named)
`MUI_RequestA`, `MUIM_Application_OpenConfigWindow`, the Popasl/Popobject requester (a press is a named refusal), NList / TextEditor / BetterString / TheBar and every other MCC's own behaviour (the classes LOAD from disk; what they need next is named in the census),
multi-selection, list sorting with a compare hook, drag and drop, scrollbars on a Scrollgroup (its contents show at their natural size).
