# Custom window definitions (WDEF) for the Mac engines: Astra's ruling (2026-10-20)

Seats asked: openai/gpt-6-astra, google/gemini-2.5-pro (both answered). Astra's seat, verbatim, is the ruling taken (the owner's standing instruction: consult Astra and take the recommendation). The council synthesis preferred Gemini's option B (a frameless window presenting the WDEF's own drawing) for Q1; Astra rejected B as a substitute for native presentation, and Q1 follows Astra: C, refusal by name. The brief is beside this file.

### Seat: `openai/gpt-6-astra`
*Verdict: Ruling: C for an arbitrary custom WDEF under the current seam and native-only acceptance bar. A is permitted only through an explicit, behavior-preserving native presentation contract; calling wHit and hiding wDraw does not establish that contract. B is an honest compatibility mode, but it does not meet the stated product requirement and is not approved as its substitute. For WDEF 128, choose iii now: named refusal until general cross-ISA execution exists. Prepare WDEF 129 through the existing CFM loader, but distinguish callback execution support from permission to present its window. First land a witnessed-red guard against silently treating an unsupported WDEF as a native document window. The supplied references contain useful implementation and testing precedents, but no direct classic Mac WDEF implementation or Linux/Haiku/FreeBSD/i915 WDEF precedent; exact historical message sequencing still requires a pinned Mac contract and execution oracle.*
- **1. Q1: Refuse unsupported presentation; do not counterfeit native compatibility**: Choose C for custom WDEFs without an explicit presentation contract. Decode the complete procID into resource selection and variation according to the pinned Toolbox ABI; never infer the window role from procID & 7 alone. Resolve the actual resource, including overrides, rather than assuming that a familiar resource number guarantees familiar behavior. An arbitrary WDEF is a contract for drawing, regions and hit testing, not a declaration that its title, border and controls mean Document or Dialog. A native title bar with guest hit regions elsewhere creates invisible controls and false affordances. Counting that discrepancy does not repair it.
A is admissible only when a toolkit contract or version-bound declarative binding supplies the native roles, coordinate mapping and interaction semantics. Such a binding must preserve the guest-visible callback effects, drawing state, readable drawing results where observable, regions and event order. Execute wDraw; do not simply skip it. Its presentation may be replaced by the contracted native rendering, but arbitrary guest-visible effects may not be discarded. Record a native-role route with binding identity and a separate presentation-substitution count; never count an unbound custom frame as native. A contract must cover the behavior actually exercised, not merely identify a code blob.
B would require new frameless/shape/input-region semantics in guestui-abi and would remain a replayed/raw custom frame, even if it occupies a host window. It can be proposed separately as an explicitly degraded compatibility mode, but cannot satisfy the owner's indistinguishable-native requirement. WDEFShell item 4 therefore does not become product-supported merely because its callback executes.
  - *Rationale*: Native hosting and native semantic presentation are different claims. The supplied WebKit theme adapter receives already-classified controls through paintButton, paintCheckbox and related methods; it does not infer controls from arbitrary drawing. That is the correct analogy for an admissible native WDEF translation. Its named fallback is an example of honest degradation, not permission to mislabel a custom frame.
- **2. Q2: Implement the Window Manager contract, not a callback demonstration**: Make strucRgn, contRgn and updateRgn real guest RegionHandles, with valid master pointers, relocatable storage and correct QuickDraw region encoding and operations. Support nonrectangular region algebra, clipping and membership; a bounding rectangle is not an equivalent implementation. Write windowDefProc as the guest WDEF resource Handle required by the WindowRecord ABI, not the host callback pointer or the UPP found inside the resource. Pin the supplied offsets 114, 118, 122 and 126 against the supported WindowRecord layout, including the corresponding NewCWindow layout. The port bounds/origin, visibility, hilite state, title, variation, window-list membership and resource lifetime must also be real wherever callbacks can observe them.
The initial logical chain is record/port/handle initialization, wNew, wCalcRgns, then the visibility, clipping, activation and drawing work required by the original Window Manager. Do not assume all guest-list insertion and activation occur after callbacks: pin their exact positions to the supported Mac version's oracle. wNew and ordinary wCalcRgns use their contract's unused parameter value, normally zero. Pass the real variation argument, not a derived host role.
Send wDraw with parameter zero for a whole-frame draw. For partial frame redraws, use the documented WDEF part selector, not an arbitrary dirty rectangle or an unconverted FindWindow result. Exercise initial visible drawing, exposure and activation/deactivation as applicable. Frame repaint and application content update events are different operations; do not equate every update event with wDraw.
FindWindow must invoke wHit for eligible windows in the original front-to-back search order, with its global Point packed according to the Toolbox ABI. Translate its WDEF hit result through an explicit mapping to the public FindWindow part code. A rectangle may be a validated conservative accelerator, never the hit-test authority. Send wDispose on the corresponding disposal path while the record, regions and WDEF resource remain usable, then perform the appropriate CloseWindow/DisposeWindow ownership cleanup. Send wGrow when GrowWindow requires its outline operation, using the documented rectangle-pointer parameter; send wDrawGIcon for DrawGrowIcon. Do not synthesize either at creation, and do not claim them exercised unless a test actually requests them.
For WDEFShell, evidence must include the menu action, callback arguments and order, resulting regions, content/drag/outside hit results, actual frame draw output, and disposal. The sample's no-op wGrow and wDrawGIcon still require correct dispatch when requested. Launching to WaitNextEvent proves none of these.
  - *Rationale*: Observable ordering is part of compatibility. WebKit's dispatchEventsOnWindowAndFocusedElement deliberately orders element blur before window blur and element focus after window focus, and suppresses delivery during its specified deferred-loading condition. This supports the need for explicit event-order tests, not any particular Mac ordering. The supplied corpus does not establish the exact Mac parameter selectors or lifecycle interleavings; obtain those before encoding them as production constants.
- **3. Q3: Refuse the 68k bridge now; do not install a sample-shaped interpreter**: Choose iii for the current implementation: refuse item 3 with a reason such as WDEF_REQUIRES_68K_EXECUTION, before beginning the window lifecycle or publishing a host window. Item 4 may become executable after fragment preparation, but remains subject to presentation admission.
The long-term implementation is i: the existing 68k interpreter and PowerPC interpreter participate in one cross-ISA callback frame machine over the same guest address space and Toolbox state. Execute the stub's instructions, enter the real $AAFE descriptor dispatch, run PowerPC with its prescribed register frame, and unwind through the matching 68k and PowerPC continuations. There must not be a second descriptor parser or a recursive interpreter-to-interpreter host call stack.
Reject ii as the production path. Recognizing executable bytes is not, by itself, the native-role inference prohibited by RETRO-ROLES-REQUIRE-A-CONTRACT. Nevertheless, a documented code idiom is not automatically a new resource format that authorizes bypassing instruction execution. Supporting only these ten bytes would make code-shape recognition the compatibility architecture. A later optimization could recognize it only over an already-correct execution path, with exact side-effect equivalence and a real interpreter fallback. It is not the way to claim cross-ISA support today.
  - *Rationale*: The supplied Ferrix architecture notes illustrate why machine-entry register and stack effects are contracts rather than incidental code shape: their x86_64 syscall entry and ARM entry paths must perform the architecture's actual transition. This is an analogy, not a source for Mac Mixed Mode semantics. Reusing the existing interpreter preserves the same distinction.
- **4. Q4: Prepare embedded fragments through one transactional CFM path**: Yes: extend the existing CFM loader with a bounded in-memory fragment source. The existing PEF parser, import resolver, section allocator, relocation engine, initialization handling and connection lifetime remain the only implementations. Decode the relative RoutineDescriptor through the existing descriptor parser, resolve its relative fields using the documented base and checked arithmetic, prepare the embedded fragment, and produce the actual callable entry/TOC through CFM semantics. Never treat the PEF container start as a function address.
Represent preparation as explicit Unprepared, Preparing, Prepared and Failed state associated with the relevant guest resource/descriptor incarnation and CFM connection. Handle initialization callbacks through the same continuation machine. Concurrent or reentrant requests must not double-prepare, observe partially relocated code or deadlock waiting on their own preparation. Pin the backing during use and define what happens when guest code changes or disposes it.
Named refusals include malformed/truncated descriptor, unsupported version/ISA/procInfo/flags, invalid relative range, missing preparation facility, unsupported import, unsupported relocation, invalid section index, relocation write outside an allocated target section, invalid callable entry/TOC, resource exhaustion and preparation reentrancy that cannot be represented correctly. Refuse known unsupported imports and malformed relocation plans before running fragment initialization.
Do not reject every relocation whose resolved address is outside the container: valid imports and separately allocated sections naturally resolve outside the original byte range. Container reads must be within the input, relocation writes within owned mapped sections, and targets within the loader's permitted address model. Do not promise rollback of arbitrary guest side effects after an initializer has executed; clean up loader-owned resources and report that failure stage honestly.
  - *Rationale*: One fact and one mechanism should have one owner. The supplied Coral physical-memory adapter demonstrates reusing SYSINFO rather than creating a second source for the same fact. The Ferrix certification excerpt also provides a useful fail-before-change precedent in its namespace-validation discussion, but it is documentation referring to Linux, not a directly supplied Linux implementation.
- **5. Q5: Split NewWindow into resumable phases with explicit publication boundaries**: WindowDefinition{window, message, phase} is only the tag. Store a typed pending-operation record containing the original trap return context, arguments, window incarnation, owned temporary resources, selected WDEF/variation, initialization state and exact next phase. Save ownership-bearing state in the engine, not in guest-controlled pointers or shared-library statics.
NewWindow entry decodes and validates arguments, resolves execution support and presentation admission, checks caller storage, and reserves resources. Known unsupported cases refuse here, before wNew. Construct the real provisional guest record, port and region handles once. Make guest list/visibility state observable at the phase required by the Mac oracle. Schedule wNew and suspend the trap; do not return to the application.
AfterNew validates the window incarnation and callback outcome, then schedules wCalcRgns. AfterCalc validates region handles and encoding and establishes the required clipping, visibility and update work. Schedule any required wDraw and other lifecycle work through further typed phases. After the required callbacks complete, commit host publication at its defined point and finish the original trap with the original WindowPtr. A hidden NewWindow does not acquire an invented draw simply to exercise a callback. GetNewWindow and NewCWindow enter this common lifecycle after their own decoding and initialization; they do not duplicate it.
Every resume enters its next phase directly. It must never rerun NewWindow's allocation, resource acquisition, list insertion or callback dispatch. Revalidate generation and lifecycle state after every callback because nested guest calls can move, close or dispose the target. Preserve legitimate nested effects; do not restore a stale snapshot over them. Handle callback faults with explicit local cleanup and the compatibility fault policy. Use a null WindowPtr or another guest return only where the supported Toolbox failure contract permits it; do not invent a successful-looking recovery after malformed guest behavior.
  - *Rationale*: The reference capability test requires an object to resolve to the exact domain it names, rejects unknown identities and rejects zero-valued empty slots. Apply that identity discipline to pending window operations: a recycled guest address must not resume an operation on a different window. The reference event-order code reinforces that callback phases cannot be freely reordered.
- **6. Q5: FindWindow resumes its search, never restarts its trap**: FindWindow entry validates its output pointer and captures the global point and original return context. Handle menu/system-window cases through the real Window Manager ordering. For ordinary windows, retain the current candidate incarnation and a resumable search position; do not hold a mutable window-list borrow across guest execution. Schedule wHit with the ABI-packed point.
AfterHit validates the candidate lifetime and returned WDEF code. For wNoHit, resume the remaining search without repeating callbacks already performed unless the original Mac semantics explicitly require reconsideration after a list mutation. For a documented hit, map it to the public part code, write the matching WindowPtr once, and finish the original trap. For no matching window, return the documented desktop/no-window result. Specify list-mutation behavior using the same oracle as creation; a stale vector of guest pointers is not a reentrancy policy.
An unknown hit code is a named WDEF_BAD_HIT_RESULT compatibility fault, not an implicit drag, content hit or wNoHit. If the reference OS specifies behavior for that value, implement it; otherwise do not pretend a chosen fallback is compatibility. A callback that leaves contRgn untouched is tested against its promised behavior: for WDEFShell's nonempty content window, the post-call expected region must fail. Do not make 'must write contRgn on every call' a universal rule, because a valid implementation may retain an already-correct region.
For nesting, drive WDEF -> Toolbox trap -> another callback -> return through explicit frames. Assert exact message order, original trap return PC, stack pointer, register restoration, one-time output writes and a bounded host call stack. Engine memory budgets may refuse further frame admission before the new callback starts; a wall-clock timeout must not manufacture a callback return.
  - *Rationale*: The supplied allocator test explains why one-sided validation misses implementations that refuse everything, and why independent expected results matter. FindWindow tests must therefore prove both correct hits and correct rejection, including nonrectangular holes and overlapping windows. The Ferrix excerpt explicitly tests iterative rather than recursive release; similarly, callback nesting must measure host recursion, not merely survive a shallow example.

[§9 · WARN] CONSEQUENCES: This ruling deliberately reduces the apparent compatibility count by exposing windows that were previously misrepresented. Native-only support for arbitrary custom WDEFs is impossible without additional semantic knowledge; the owner must accept named refusals, approve adequate bindings, or separately relax the presentation requirement. Bindings create versioning and maintenance obligations. Real region/drawing observability increases engine state, and reentrant fragment preparation increases lifetime complexity. General cross-ISA execution benefits other Toolbox callbacks but materially enlarges the verification surface. These consequences are advisory, not permission to bypass the guardrails. No repository inspection, compilation, boot or Mac-oracle execution was performed for this answer.
  - *Rationale*: The supplied references support exact identity, independent behavioral oracles, explicit event ordering and call-local rendering storage. They do not certify this implementation or establish a Mac platform branch. A production ruling must state that evidence boundary rather than dressing unrelated citations as proof of WDEF semantics.
