# Mac OS 9.2.1 fact oracle (from the owner's own install CD)

Source: Peter's original Mac OS 9.2.1 CD image (sha256 `2fe852fae744cf9fab19c2e2ff779bd46e4493aab68f79cad0501cbeeac51db2`). Owner-supplied reference input: no byte of it is in this
repository, nothing was executed, and only facts (numbers, names, layouts, observed instruction shapes) are written down. Everything extracted lives in
`/data/build/corpus-bin/mac/macos921/` (`out/` MacBinary II files, `pef/` + `pef-rom/` cut-out CFM containers, `rom/` decompressed ROM parcels and the 4 MB ROM image, `exports/`
per-library export lists, `libs.tsv` the census of 617 distinct containers). Rows are in `CORPUS.tsv`. Throwaway tools (PEF/cfrg/resource-fork readers, `llvm-mc` PowerPC
disassembly) were in `/tmp/claude-1000/tools`, not in the repo. Citation form: "CarbonLib 1.4 data@0xC3B8" = byte offset in that container's data section 1; "NQD `NQDNewGWorld`
+0x..." = offset in code section 0.

## 1. What is on the CD

* Apple partition map; one classic HFS volume "Mac OS 9.2.1" (640 MB; `machfs` reads it, `7z` does not). 2268 files: `System Folder` (860), `Software Installers` (808: the Apple
  Installer "Tome" archives plus IE/Netscape/MRJ/DVD), `CD Extras` (585), `Utilities`, the `Install Mac OS 9.2.1` application.
* The boot System Folder is real and complete: `System` (zsys, 14 MB; its data fork holds ~96 named PEF libraries listed by its `cfrg`), `Mac OS ROM` (tbxi, a New World
  `<CHRP-BOOT>` file whose parcel area at 0x1BFC0 holds LZSS-compressed `nlib/shlb/ndrv` parcels and a `rom ` parcel = the 4 MB Toolbox ROM image), `Extensions/CarbonLib`
  (INIT/cbon, 16 CFM fragments in its data fork), `Extensions/QuickTime PowerPlug`, `Open Transport`, `Text Encoding Converter`, `Multiprocessing/Apple CPU Plugins`, ...
* `Software Installers/System Software/Mac OS 9.2.1/Big System Morsels` (resource fork, 153 PEF resources) is the ROM build's source libraries WITH NAMES (`nlib`/`fovr`/`sfvr`
  resource names); that is how the ROM image's anonymous PEFs were identified (same bytes).
* NOT opened: `Installation Tome` (52 MB) and `QT Tome` (Apple Installer archives, header `kc 00 01`, per-file records with name/type/creator). Their file tables list `OpenGLLibrary`,
  `OpenGLEngine`, `OpenGLUtility`, `OpenGLRenderer`, `OpenGLRendererATI`, `NVIDIA OpenGL`, `DrawSprocketLib`, `InputSprocket Extension`, so **OpenGL, DrawSprocket and InputSprocket
  exist only inside the Tomes**; their compression is not a format `unar`/`7z` knows. A Tome unpacker is the missing piece for those three. QuickTime is available (PowerPlug).
* `System` and the installer's `System Extras` carry the same data fork (same offsets); `libs.tsv` is deduplicated by sha256.

## 3. The open questions

### (a) Carbon Event Manager constants (CarbonLib 1.4)
Evidence: CarbonLib's static `EventTypeSpec` tables (8-byte {class, kind} pairs) in data section 1, plus four-char-code loads (`lis/ori`, `li/addis`) in code.
* Standard window handler table, data@0xC3B8: `mous/1, cmds/1, cmds/2, wind/2, wind/1, wind/6, wind/5, wind/201, wind/37, 38, 32, 33, 34, 36, 35, 41, 7, cntl/13, wind/66, 69, 68, 71, 75, 72, 77, 74, 83`.
  So class `wind`: Update 1, DrawContent 2, Activated 5, Deactivated 6, Close 72. **73 (the engine's Closed) is in no table.**
* Application table, data@0xBF40: `appl/1, appl/2, appl/3, cmds/1, eppc/1`: class `appl`, Activated 1, Deactivated 2, Quit 3.
* Mouse, data@0xC180: `mous/5, 6, 1, 2` (Moved 5, Dragged 6, Down 1, Up 2). Keyboard, data@0xC0D8 and 0xC180: `keyb/1, 2, 3, 4` (RawKeyDown, Repeat, Up, Modifiers).
* Command class is `cmds` (Process 1, UpdateStatus 2: data@0xBE68, 0xDFA0, and in `Textension_CL`); menu class `menu` (4, 8 seen); control class `cntl` (13, 159).
* Parameter / type codes the code loads: `----` (32 uses), `mloc` (7), `mbtn` (8), `kmod` (15), `kcod` (3), `kchr` (6), `ccnt` (2), `hcmd` (9); types `magn` (56), `TEXT` (22), `mbtn`, `wind`, and **`QDpt` (20 uses; `QDPt` occurs nowhere)**.
* Errors as immediates: `-9874` eventNotHandledErr (40+ sites), `-9875` eventLoopTimedOutErr (event-loop / WaitNextEvent-family code), `-9870` eventParameterNotFoundErr (inside GetEventParameter), also -9868/-9866/-9864.

**Mismatch found: the engine's `T_QDPOINT` was `'QDPt'`; the OS uses `'QDpt'`. Fixed.** Everything else `carbon.rs` uses is confirmed, except `kEventWindowClosed = 73`, which the tables neither confirm nor deny.

### (b) Multiprocessing Services error codes (MPLibrary 9.2.1 and the NanoKernel in the ROM image)
`li r3,imm` census in MPLibrary: -29299 x3, -29298 x86, -29296 x6, -29295 x1, -29294 x22, -29293 x9. The NanoKernel has the same set as an error-exit ladder at ROM-image 0x31A2A0..0x31A3E8
(-29294, -29295, -29296, -29297, -29298, -29293, -50, -29276, -29299, -29274) and also -29292, -29291, -29287..-29285.
* -29296 = kMPTimeoutErr: in `MPDelayUntil` (+0x6214..0x6238) the result -29296 is the success exit of the delay loop; -29293 selects the blue-task retry path.
* -29298 = kMPInsufficientResourcesErr: the dominant code of every allocating or creating call (86 sites).
* -29299 = kMPInvalidIDErr and -29295 = kMPDeletedErr: the numbers are present; the names cannot be proven from code (no symbols in the traceback tables) but agree with the header values I know.
* -29297 (kMPTaskAbortedErr) occurs only in the kernel (9 sites); -29294 is returned by every Create* call and MPTerminateTask (name unproven).
**No mismatch**: `mp.rs` uses -29295/-29296/-29298/-29299 and all are right. Not modelled by the engine: -29297, -29293, -29294.

### (c) GWorld (PPC `NQD`, `NQDNewGWorld` at +0x2FF70)
* Registers: r3 `&gworld`, r4 depth, r5 bounds, r6 cTable, r7 aGDevice, r8 flags (kept in r28).
* Flags tested: `rlwinm r,r28,0,30,30` = **0x02 noNewDevice**; `0,29,29` = **0x04 useTempMem**; `0,27,27` = **0x10** and `0,26,26` = **0x20** (useDistantHdwrMem / useLocalHdwrMem); `0,17,17` = **0x4000**
  (kAllocDirectDrawSurface). The inner allocator (+0x2FA50) tests the same 0x04/0x10/0x20. pixPurge (1) and keepLocal (8) are not tested as plain bits in these two routines (their values come from Gestalt-era headers; not contradicted).
* Depth: 24 is promoted to 32 (`cmpwi r27,24; li r27,32`); depth >= 33 returns **-157 (cDepthErr)**; a null `&gworld` or an invalid/empty bounds returns **-50**; allocation failure **-108**.
  With noNewDevice set a null device is -50 and the depth is read from that device's PixMap `pixelSize` (`lha r25,32(pixmap)`); without it the device is `TheGDevice` (low-memory 0xCC8 = 3272).
* **Depth 0** is not an error: the `cmpwi r27,0` branch at +0x30190 takes the colour table from the device's PixMap (`pmTable`, PixMap+42), i.e. depth 0 = "use the device's depth and colour table".
* The engine has no GWorld yet (only `pixmap.rs` rowBytes), so nothing to compare; this is the oracle for the worker implementing it. `gwFlagErr` (high bit of UpdateGWorld's result) was not traced.

### (d) List Manager `lDrawingModeOff`
`ListsLib` `_eLSetDrawingMode` (+0x181C): `lbz r0,39(r5)` on the ListRec (listFlags at offset 39); drawIt FALSE: `ori r0,r0,8; stb`; TRUE: `rlwinm r0,r0,0,29,27` (clears 0x08) and then a redraw.
**Confirms `lDrawingModeOff = 0x08` at offset 39**, matching `translate/lists.rs` and its test.

### (e) CarbonLib Gestalt
CarbonLib's INIT 0 (68k, 2782 bytes) at +0x2D0: `move.l #'cbon',-(sp); pea $0140.w; ...` then the Gestalt-install trap ($ABF1, d0 = $0401): **Gestalt `'cbon'` = 0x0140 (1.4.0 BCD)**; it also installs `'cmem'` = 0x0003D090.
`ProcessMgrLib` references 'cbon' too. The engine deliberately leaves 'cbon' unanswered (`gestalt_ppc.rs`); when CarbonLib support is real, 0x0140 is the number for the 1.4 behaviour.

### Mismatch list
1. `carbon.rs`: `QDPt` should be `QDpt` (typeQDPoint). FIXED, with the test constants.
2. Unverified, not wrong: `kEventWindowClosed = 73`.
Everything else compared (classes and kinds of mous/keyb/wind/appl, parameter codes, -9874/-9875/-9870, MP error numbers, lDrawingModeOff) matches.

## 4. Option for later: load Apple's own shared libraries from the user's copy

The engine already loads private fragments (Miles, StormCarbon). The same loader could load Apple's PEF libraries from the user's System Folder ("the user supplies their OS").
* **Self-contained enough (they import only each other, MathLibGlobals, or a few InterfaceLib symbols):** `MathLib` (imports only `MathLibGlobals`), `vecLib` (MathLib + 3 InterfaceLib), `TextCommon`/`UnicodeConverter`/TEC (InterfaceLib only),
  `LocalesLib`, `SoundLib` (3 InterfaceLib), `ThreadsLib` (13 InterfaceLib + 3 Private), `ObjectSupportLib` (35 InterfaceLib + `OSLData`), `NavigationLib` (21 InterfaceLib). `StdCLib` needs 55 InterfaceLib + MPLibrary + MathLib.
* **Everything funnels through `InterfaceLib`/`PrivateInterfaceLib`** (2820 + 1000 exports): they ARE the trap surface, on low memory, Mixed Mode, the 68k emulator and CodeFragmentMgr, and cannot be loaded; the engine keeps providing them natively and the Apple leaf libraries would call into that.
* **Do not load:** AppearanceLib/ControlsLib/WindowsLib/MenusLib/MacDialogsLib (285/95/227/195 InterfaceLib imports plus `NQD`, `ToolboxUtils`, `BlueAbstractionLayerLib`) drag in the whole Toolbox with private structures and would bypass the Gute Form drawing path; MPLibrary needs the NanoKernel (`sc` into ROM code); NQD needs low-memory QuickDraw globals and GDevices; drivers (`ndrv`/`nlib`) need hardware.
* **Recommendation:** an opt-in "user-supplied libraries" mode (a user directory, resolved by `cfrg` name+version out of `System`, like the Amiga ROM/Kickstart arrangement), starting with MathLib, then vecLib, TextCommon/UnicodeConverter, LocalesLib, ThreadsLib. Keep the native MP/Threads/Carbon Events; use the real binaries chiefly as a **differential oracle** (MathLib's long-double behaviour is a classic bug source and the real library is byte-exact reference). Legal: the user supplies files from a copy they own; nothing is shipped, committed or redistributed, with a visible notice.
